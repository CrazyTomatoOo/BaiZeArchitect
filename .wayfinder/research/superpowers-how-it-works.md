# Superpowers 工作原理

## Question

Superpowers（GitHub `obra/superpowers`，自述 "An agentic skills framework & software development methodology that works."，MIT，主语言 Shell）**机制上**是如何工作的：一个 skill 的磁盘契约是什么、谁把 skill 清单注册进 harness、会话开始时什么文本被注入上下文、同一套 `skills/` 如何被各 harness 各自加载（树内共 10 份 harness 专属打包产物 + 1 份厂商中立 `.agents`）、15 个 skill 之间如何串成方法论链条、哪些部分是机械执行（脚本/钩子/manifest）而哪些只是模型可以无视的散文。

范围：以 `main` HEAD `5bf4e78011075bcfc0dc295f0724994cd123ee71`（下称 `@5bf4e780`，提交信息 "Release v6.4.1"，2026-09-18T17:31:35-07:00）为准；版本号 **6.4.1**（`package.json`、`.claude-plugin/plugin.json`、`.codex-plugin/plugin.json`、`.kimi-plugin/plugin.json`、`.muse-plugin/plugin.json`、`.cursor-plugin/plugin.json`、`.devin-plugin/plugin.json`、`.claude-plugin/marketplace.json`、`.muse-plugin/marketplace.json`、`gemini-extension.json`、`.hermes-plugin/plugin.yaml` 全部一致，由 `.version-bump.json` 集中声明，obra/superpowers@5bf4e780）。行为类结论附本地实测（同 SHA 克隆上直接运行 hook、Claude Code CLI 端到端探针、`claude plugin validate` 正/反例），标注 "本地实测（obra/superpowers@5bf4e780）"。

不在范围内：与其他框架的对比（仅一行事实性对比，见 §7 末）；对 skill 散文内容质量的评估（只描述机制）；`skills/brainstorming/visual-companion.md` 涉及的浏览器伴生工具的设计细节（仅提及其存在）。

**身份核验**：repo 自述与主代理提供的 GitHub API 事实一致；npm 上名为 `superpowers` 的包是**无关项目**（v0.0.2，description 为 "> TODO: description"）——Superpowers **不在 npm 分发**，本仓库的 `package.json` 存在意义是让 OpenCode 插件可加载（`"main": ".opencode/plugins/superpowers.js"`，无 `bin`/`scripts`/`files`），安装路径只有 git marketplace / `--plugin-dir` / 复制 `skills/`（本地实测（obra/superpowers@5bf4e780）；package.json, obra/superpowers@5bf4e780）。

## Findings

### 0. 机制总览：一句话两层皮

- Superpowers 的全部机制 = **一套磁盘上的 skill 库（`skills/<name>/SKILL.md`）+ 每个 harness 的一次会话启动注入（bootstrap）**。没有任何守护进程、没有运行时服务、没有 hook 之外的中间件；除会话启动注入外，框架对模型的全部"约束力"都写在 SKILL.md 散文里（hooks/session-start:1-53、.pi/extensions/superpowers.ts、.opencode/plugins/superpowers.js, obra/superpowers@5bf4e780）。
- 注入的 bootstrap **只有 1 个 skill 的全文**（`using-superpowers`），其余 14 个 skill 不进入上下文，只存在于 harness 的 skill 注册表里、由模型按需通过 harness 原生的 skill 工具加载（本地实测（obra/superpowers@5bf4e780）——payload 3,616 字节，恰为 `using-superpowers/SKILL.md` 全文；探针询问 `EXTREMELY_IMPORTANT` 块内首句，模型准确答出 "You have superpowers."）。

### 1. 一个 skill 在这里是什么：SKILL.md 契约

- **目录布局**：`skills/<kebab-name>/SKILL.md` 为唯一必需文件，旁挂任意支撑文件（prompt 模板、脚本、references）。`writing-skills` 自己规定的结构："Frontmatter (YAML): Two required fields: `name` and `description`… Max 1024 characters total… `description`: Third-person, describes ONLY when to use (NOT what it does)… Start with 'Use when...'"，且明令 description **不得概括工作流**——"**The trap:** Descriptions that summarize workflow create a shortcut agents will take. The skill body becomes documentation agents skip."（skills/writing-skills/SKILL.md:140-158, obra/superpowers@5bf4e780），并给出实证（某 description 写 "code review between tasks" 导致 agent 只做一次 review；改成纯触发条件后 agent 才读流程图做两阶段 review）（skills/writing-skills/SKILL.md "SKILL.md Structure" 与 "Skill Discovery Optimization (SDO)" 节, obra/superpowers@5bf4e780）。
- **frontmatter 是 convention 而非 enforcement**：本仓库 15 个 SKILL.md 的 frontmatter 只有两个字段 `name` 与 `description`（逐一核对 skills/*/SKILL.md 头部, obra/superpowers@5bf4e780）。`claude plugin validate` 对故意缺失 `description`、完全没有 frontmatter 块的 skill 只给 **warning**（"No description in frontmatter…"、"No frontmatter block found…"），对 `name: Bad Name With Spaces` 甚至无任何 finding——全部 exit 0（本地实测（obra/superpowers@5bf4e780），scratch 插件 + 三个故意违规 skill）。即：**连 harness 自己的校验器也只把发现性契约当警告**；对照 OpenSpec 的 `validate --strict` 把 warning 变成失败（见姊妹篇），两项目在这条线上处于相反两端。
- **`skills/using-superpowers/` 是什么、为什么存在**：它是"技能的技能"——`description: Use when starting any conversation - establishes how to find and use skills, requiring skill invocation before ANY response including clarifying questions`。正文只有一条 The Rule（"Invoke relevant or requested skills BEFORE any response or action — including clarifying questions"）、一张 "Red Flags" 合理化表格、Platform Adaptation 指针和用户指令优先级条款（skills/using-superpowers/SKILL.md, obra/superpowers@5bf4e780）。它存在的理由：其余 14 个 skill 只有 description 一行进了 harness 的注册表，**谁来决定"何时该读哪个 skill"这件事本身必须被注入上下文**，否则整个库是死文件——上游 AGENTS.md 说得很直白："The bootstrap is what causes skills to auto-trigger at the right moments. Without it, the skills are dead weight — present on disk but never invoked"（AGENTS.md "New Harness Support", obra/superpowers@5bf4e780）。
- **references/`<harness>`-tools.md 的适配机制**：`using-superpowers/SKILL.md` 正文列了 6 个 harness 指针（Claude Code / Codex / Pi / Antigravity / Hermes / Muse），目录里实际有 7 个文件（多 gemini-tools.md）。每个文件把 skill 散文里的动作词映射到该 harness 的工具名与限制：如 `pi-tools.md` 说明 "Pi core does not ship a standard subagent tool… If no subagent tool is available, do not fabricate `Task` calls"；`codex-tools.md` 说明 `spawn_agent {fork_turns:"none"}`、`wait_agent` 是事件订阅不是轮询、V1/V2 生命周期差异（skills/using-superpowers/references/pi-tools.md、codex-tools.md、claude-code-tools.md, obra/superpowers@5bf4e780）。**同一个 skill 靠"模型读对应参考文件后自行翻译工具名"来跨 harness 复用**，没有代码层的适配器。

### 2. 引导/注入机制：会话启动时到底发射什么

- **触发器**：`hooks/hooks.json` 把 `hooks/session-start` 注册为 Claude Code 的 `SessionStart` hook，`matcher: "startup|clear|compact"`，`async: false`（hooks/hooks.json, obra/superpowers@5bf4e780）。即启动、/clear、compact 三种事件都重注入。Cursor 用 `hooks/hooks-cursor.json`（`sessionStart: [{"command": "./hooks/run-hook.cmd session-start"}]`），Muse 在 manifest 里内联声明同一个 hook（hooks/hooks-cursor.json、.muse-plugin/plugin.json "capabilities.hooks", obra/superpowers@5bf4e780）。
- **`hooks/session-start` 的发射物**（bash）：读取 `skills/using-superpowers/SKILL.md` 全文 → JSON 转义 → 包成 `session_context="<EXTREMELY_IMPORTANT>\nYou have superpowers.\n\n**Below is the full content of your 'superpowers:using-superpowers' skill - your introduction to using skills. For all other skills, use the 'Skill' tool:**\n\n…\n</EXTREMELY_IMPORTANT>"`（hooks/session-start:27, obra/superpowers@5bf4e780），然后按平台环境变量四选一输出信封（hooks/session-start:39-53）：`CURSOR_PLUGIN_ROOT` → 顶层 `additional_context`；`CLAUDE_PLUGIN_ROOT`（非 Copilot/Muse）→ `hookSpecificOutput.additionalContext`；`MUSE_PLUGIN_ROOT` → Claude 式嵌套；否则（Copilot CLI 等）→ 顶层 `additionalContext`。脚本注释记录了为什么必须区分："Claude Code reads BOTH additional_context and hookSpecificOutput without deduplication, so we must emit only the field the current platform consumes"，以及 bash 5.3+ heredoc 挂起的 workaround（改用 `printf`，issue #571）（hooks/session-start:29-38, obra/superpowers@5bf4e780）。`exit 0` 无条件成功（hooks/session-start:53）。
- **实测确认**（本地实测（obra/superpowers@5bf4e780））：直接运行三分支（`CLAUDE_PLUGIN_ROOT` / `CURSOR_PLUGIN_ROOT` / `COPILOT_CLI=1`），输出 JSON key 分别确为 `hookSpecificOutput` / `additional_context` / `additionalContext`；端到端用 `claude -p --plugin-dir <clone>` 在空目录提问，模型准确复述注入块首句 "You have superpowers."——即 additionalContext 真的到达模型上下文。
- **`hooks/run-hook.cmd`** 是 cmd/bash 双语 polyglot：Windows 下定位 Git for Windows 的 bash 执行同名脚本，找不到 bash 则 `exit /b 0` 静默成功（注释原文："plugin still works, just without SessionStart context injection"）；hook 脚本故意无扩展名，以免 Claude Code 的 Windows 自动检测prepend `bash`（hooks/run-hook.cmd, obra/superpowers@5bf4e780；本地实测确认双语文本）。
- **skill 清单如何被模型知晓**：**不是注入，是索引**。插件加载时 harness 扫描 `skills/` 目录，把每个 SKILL.md 的 `name`/`description` 注册为命名空间 `superpowers:<name>` 的 skill；模型只看到这些 description 行。实测：限制只有 `Skill` 工具时，模型可正确报出 `superpowers:writing-skills` 与 `superpowers:test-driven-development` 的 description 原文；但用**不存在的名字**探针只回 "Unknown skill: <name>"——**不会枚举可用 skill 清单**（本地实测（obra/superpowers@5bf4e780））。`claude plugin validate` 对整仓与 `skills/` 目录均 "Validation passed"（本地实测）。
- **非 Claude 系 harness 的等价注入**（各自独立实现，见 §3）：
  - **Pi**：`.pi/extensions/superpowers.ts`（针对 `@earendil-works/pi-coding-agent`）。`pi.on("resources_discover")` 返回 `{skillPaths: [skillsDir]}` 注册全部 skill；`pi.on("context")` 在 `firstNonCompactionSummaryIndex` 处插入一条合成 `{role:"user"}` 消息携带 bootstrap（剥掉 frontmatter + 追加 `piToolMapping()` 附录），用 `messageContainsBootstrap` 去重；`injectBootstrap` 在 `session_start`/`session_compact` 置 true、在 `agent_end` 置 false（.pi/extensions/superpowers.ts:28-63、66-117, obra/superpowers@5bf4e780）。
  - **OpenCode**：`.opencode/plugins/superpowers.js` 双形态：V1（1.x）用 `config` hook 把 `skills/` 塞进 `config.skills.paths`、用 `experimental.chat.messages.transform` 向首个 user 消息 `unshift` bootstrap；V2（2.0.4+）用 `setup(ctx)` 把每个 SKILL.md 逐条 `ctx.skill.transform(draft => draft.add({id,name,description,path,content}))` 注册为原生 Skill.Info，并用 `ctx.session.hook("context")` 注入。两者都按 `session.parentID` **结构性地区分子会话**（task subagent 不注入 bootstrap，避免 worker 重启 controller 工作流，注释引 issue #2160；缓存上限 512 条）（.opencode/plugins/superpowers.js "V1 Plugin Function"/"V2 Setup Function"/"Task-subagent detection" 节, obra/superpowers@5bf4e780）。`index.js` 仅是 V2 目录形态插件的入口，re-export `./.opencode/plugins/superpowers.js`（index.js, obra/superpowers@5bf4e780）。
  - **Hermes**：`.hermes-plugin/plugin.py`（manifest `provides_hooks: [pre_llm_call]`）在每次 LLM 调用前构建同样的 `<EXTREMELY_IMPORTANT>` bootstrap，并把 `references/hermes-tools.md` 全文作为 tool mapping 拼入；找不到 `skills/` 树时**抛 RuntimeError 而非静默跳过**（"a bootstrap that silently skips is how a broken install masquerades as a working one"）（.hermes-plugin/__init__.py、plugin.yaml, obra/superpowers@5bf4e780）。
- **上下文成本实测**（本地实测（obra/superpowers@5bf4e780），`wc -c` 于同 SHA 克隆）：
  - **常驻成本**：SessionStart payload **3,616 字节**（约 0.9k token）= 恰好一个 skill（`skills/using-superpowers/SKILL.md` = 3,192 字节）+ ~424 字节 `<EXTREMELY_IMPORTANT>` 包装。这是每个会话在用户输入任何东西之前就付的税。
  - **按需成本**：15 个 `SKILL.md` 合计 **168,882 字节**（若全部载入约 42k token）。从大到小：subagent-driven-development 32,577 · writing-skills 26,623 · executing-plans 20,405 · brainstorming 17,548 · test-driven-development 9,578 · systematic-debugging 9,465 · writing-plans 9,092 · finishing-a-development-branch 7,781 · diagnosing-superpowers 6,904 · using-git-worktrees 6,813 · receiving-code-review 6,203 · dispatching-parallel-agents 6,078 · verification-before-completion 3,646 · using-superpowers 3,192 · requesting-code-review 2,977。整个 `skills/` 树（含脚本与 reference 文件）**596 KB**。
  - **解读**：设计是"常驻索引一个 skill，其余按需加载"——常驻税被刻意压得很小；但最大的 skill（SDD，~8k token）是 bootstrap 的 9 倍，恰是方法论最依赖的那个，所以一个真跑 SDD 的会话实际付的成本远超 3.6KB 给人的印象。对照 OpenSpec：其生成的 skill 同样按需加载，但**常驻成本为零**（OpenSpec 会话启动不注入任何东西）。

### 3. 多 harness 打包：一份 skills/，N 份 manifest

- **有插件 manifest 的 harness**（共 12 份打包产物，全部指向同一份 `./skills/`）：`.claude-plugin/`（plugin.json + marketplace.json）、`.codex-plugin/plugin.json`、`.cursor-plugin/plugin.json`、`.devin-plugin/plugin.json`、`.kimi-plugin/plugin.json`、`.muse-plugin/`（plugin.json + marketplace.json）、`.hermes-plugin/`（plugin.py + plugin.yaml）、`.opencode/plugins/superpowers.js`、`index.js`、`.pi/extensions/superpowers.ts`、`gemini-extension.json`、`.agents/plugins/marketplace.json`（逐一核对上述文件, obra/superpowers@5bf4e780）。README 的安装节还覆盖 Antigravity、Copilot CLI、Qwen Code、Factory Droid、Grok Build CLI 等（从 marketplace 安装）与 pi（`pi install git:github.com/obra/superpowers`，靠 `package.json` 的 `"pi": {extensions, skills}` 块）（README.md "Installation", obra/superpowers@5bf4e780）。
- **注册方式各不相同（3+ 实例）**：
  - **Claude Code**：`plugin.json` 只声明元数据；skill 注册靠 harness 约定扫描 `skills/`；hook 靠 `hooks/hooks.json`；marketplace.json（name `superpowers-dev`）声明 `"source": "./"`（.claude-plugin/plugin.json、marketplace.json、hooks/hooks.json, obra/superpowers@5bf4e780）。
  - **Codex**：`plugin.json` 显式 `"skills": "./skills/"`、`"hooks": {}`，外加一大块 `interface`（displayName、defaultPrompt、品牌色、图标资产路径）——Codex 门户形态需要的 UI 元数据（.codex-plugin/plugin.json, obra/superpowers@5bf4e780）。
  - **Pi**：`package.json` 的 `"pi"` 块声明 extensions 与 skills 路径，扩展本身在 `resources_discover` 里注册（package.json、.pi/extensions/superpowers.ts:30-32, obra/superpowers@5bf4e780）。
  - **OpenCode**：见 §2，V1 config-hook 注入路径 / V2 setup 逐条注册（.opencode/plugins/superpowers.js, obra/superpowers@5bf4e780）。
  - **Muse/Kimi 显式列举**：Muse 的 plugin.json 把 15 个 skill 逐一 `{id, path}` 列出并内联 hook 命令；Kimi 用 `"skills": "./skills/"` + `"sessionStart": {"skill": "using-superpowers"}` + 内联 `skillInstructions` 工具映射文本（.muse-plugin/plugin.json、.kimi-plugin/plugin.json, obra/superpowers@5bf4e780）。
- **共享 vs 每 harness**：共享的**只有 `skills/` 目录本身**（与 LICENSE/README/assets）；每 harness 的注入逻辑、bootstrap 构建、工具映射都是**独立实现**（bash hook / TS extension / JS 插件 / Python hook 四种引导器，产出同一种 `<EXTREMELY_IMPORTANT>` 文本但代码零复用）。version 号靠 `.version-bump.json` 同步到全部 11 个文件。
- **codegen/sync 脚本**：
  - `scripts/sync-to-codex-plugin.sh`：把上游 checkout rsync 到 fork `prime-radiant-inc/openai-codex-plugins` 的 `plugins/superpowers/`，保留 OpenAI 拥有的 marketplace 元数据，自动开 PR；支持 `--bootstrap`、`--dry-run`、`--local`；自述 "Deterministic: running twice against the same upstream SHA produces PRs with identical diffs"（scripts/sync-to-codex-plugin.sh 头注释与 Config 节, obra/superpowers@5bf4e780）。
  - `scripts/package-codex-plugin.sh`：打 rootless tar/zip 归档（`git archive` 取 `.codex-plugin`、LICENSE、README、assets、skills），从旧官方包 seed 每 skill 的 `agents/openai.yaml` 元数据，校验 skill 数与元数据数相等、归档内无意外路径，输出 SHA-256（scripts/package-codex-plugin.sh, obra/superpowers@5bf4e780）。
  - `scripts/lint-shell.sh`：shell 脚本 lint（被 tests/shell-lint 使用）。

### 4. 方法论链条：skill 如何串成工作流

每个 skill 的 frontmatter description 即触发器（模型看到的是这一行）。按链条顺序引用各自的 "Use when…" 原文（全部出自 skills/*/SKILL.md frontmatter, obra/superpowers@5bf4e780）：

- `brainstorming`："**You MUST use this before any creative work** - creating features, building components, adding functionality, or modifying behavior. Explores user intent, requirements and design before implementation." 内部分 Spike/Bounded/Architectural 三路径， Architectural 路径产出 spec 写至 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 并 commit，然后唯一允许的下一 skill 是 writing-plans（`<HARD-GATE>` 块与 "Terminal states are path-bound", skills/brainstorming/SKILL.md）。
- `writing-plans`："Use when you have a spec or requirements for a multi-step task, before touching code"。计划存 `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`，强制 header（含 `REQUIRED SUB-SKILL:` 行、Global Constraints、Review Focus），任务粒度 2-5 分钟一步，"No Placeholders"；完成后交人审并二选一执行方式（skills/writing-plans/SKILL.md）。
- 执行二选一：
  - `subagent-driven-development`："Use when executing implementation plans with independent tasks in the current session"（§5 详述）；
  - `executing-plans`："Use when executing an implementation plan in the current session as the implementer yourself — your human partner chose inline execution, or no subagent tool is available"。同 workspace/ledger/停止规则，但无 per-task reviewer，只在末尾一次 whole-branch review（skills/executing-plans/SKILL.md；v6.4.1 把原本 64 行的 stub 重建为 "Native execution"，见 RELEASE-NOTES.md v6.4.1, obra/superpowers@5bf4e780）。
- `test-driven-development`："Use when implementing any feature or bugfix, before writing implementation code"（§6）。
- `requesting-code-review`："Use when completing tasks, implementing major features, or before merging to verify work meets requirements"——终评用其 `code-reviewer.md` 模板派发到最强模型（skills/requesting-code-review/SKILL.md）。
- `receiving-code-review`："Use when receiving code review feedback, before implementing suggestions, especially if feedback seems unclear or technically questionable - requires technical rigor and verification, not performative agreement or blind implementation"。明令禁语："You're absolutely right!" 等表演性认同（skills/receiving-code-review/SKILL.md "Forbidden Responses"）。
- `verification-before-completion`："Use when about to claim work is complete, fixed, or passing, before committing or creating PRs"（§6）。
- `finishing-a-development-branch`："Use when implementation is complete, all tests pass, and you need to decide how to integrate the work"——Verify → Detect environment → 给人出 3 选项菜单（merge/push PR/keep）→ 执行 → 清理 worktree（skills/finishing-a-development-branch/SKILL.md）。
- 链条是**交叉引用串起来的 prose**：writing-plans 的 header 写死 "REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans"；SDD 的终态是 "Use superpowers:finishing-a-development-branch"；systematic-debugging Phase 4 要求用 test-driven-development 与 verification-before-completion（skills/writing-plans/SKILL.md、skills/subagent-driven-development/SKILL.md:568、skills/systematic-debugging/SKILL.md Phase 4, obra/superpowers@5bf4e780）。**链条没有代码层编排**——完全靠模型按描述行互相点名。

### 5. subagent-driven-development 深度（568 行，本库的中枢 skill）

- **协议**：controller 会话逐任务派发 fresh implementer subagent，每个任务后一次 task-scoped review（spec 合规 + 代码质量双 verdict），全部任务后一次 whole-branch final review；"Never dispatch multiple implementation subagents in parallel"；"Never fix findings yourself in the controller session"（skills/subagent-driven-development/SKILL.md "The Process" 与 "The Task Loop", obra/superpowers@5bf4e780）。
- **三份 prompt 模板**（都是 dispatch 时填充占位符的 markdown，不是代码）：
  - `implementer-prompt.md`（154 行）：状态契约 **DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT**；要求先读 brief 文件、"You Do Not Dispatch Subagents" 条款（worker 自派 reviewer 被定义为 defect）、TDD 证据（RED 命令+失败输出 / GREEN 命令+通过输出）写入 report 文件、回复限 15 行以内（skills/subagent-driven-development/implementer-prompt.md）。
  - `task-reviewer-prompt.md`（207 行）：三输入（brief、report、diff 文件）；"Do Not Trust the Report"（"a stated rationale never downgrades a finding's severity"）；不重跑 implementer 已跑的测试；输出 Spec Compliance ✅/❌/⚠️ + Strengths + Critical/Important/Minor 分级 + Task quality verdict（skills/subagent-driven-development/task-reviewer-prompt.md）。
  - `re-review-prompt.md`（115 行）：scoped——只 verdict 既有 findings（ADDRESSED / NOT ADDRESSED）+ 查 fix diff 的新破坏，范围外观察项进 ledger 不延长循环（skills/subagent-driven-development/re-review-prompt.md）。
- **三个 helper 脚本**（机械层，bash，含 exit code）：
  - `scripts/sdd-workspace PLAN_FILE`：解析并创建该 plan 专属工作目录 `<repo-root>/.superpowers/sdd/<slug>/`，写 `plan-path` 标记防止同名 plan 串台，写自忽略 `.gitignore`；放工作树而非 `.git/` 下是因为 "Claude Code treats .git/ as a protected path and denies agent writes there"（skills/subagent-driven-development/scripts/sdd-workspace 头注释, obra/superpowers@5bf4e780）。
  - `scripts/task-brief PLAN_FILE N`：awk 抽取 plan 中 `Task N` 小节全文到 `task-<N>-brief.md`（代码围栏感知；找不到退出 3），使任务文本不经过 controller 上下文（skills/subagent-driven-development/scripts/task-brief, obra/superpowers@5bf4e780）。
  - `scripts/review-package PLAN_FILE BASE HEAD`：把 `git log --oneline` + `git diff --stat` + `git diff -U10` 写成一个 `.diff` 文件供 reviewer 一次 Read；带 range 守卫（BASE 非 HEAD 祖先、空 range → exit 3），注释强调 "Using the recorded per-task BASE (not HEAD~1) keeps multi-commit tasks intact"（skills/subagent-driven-development/scripts/review-package, obra/superpowers@5bf4e780）。
- **fix loop 如何被边界约束**：最多 **5 轮**（"Five rounds maximum per task"，skills/subagent-driven-development/SKILL.md:373）：R1-3 resume 原 implementer（保住其上下文），R4-5 换 fresh implementer 且模型升一档（"A loop that survives three resumes usually means the implementer cannot see its own problem"）；每轮 = 一次 fix dispatch + 一次 scoped re-review；Minor findings 不进循环只进 ledger；plan-mandated 的 finding 由 controller 依据 spec 裁决并记 `Ruling:`；第 5 轮仍不过 → **breaker**：controller 逐条 adjudicate（park 或 rule），且 "Adjudicating earlier to end a loop is pre-judging with a different name. Every adjudication is a ledger entry — a silent discard is forbidden"（:427-429）（skills/subagent-driven-development/SKILL.md:372-429, obra/superpowers@5bf4e780）。
- **compaction 韧性**：ledger 文件（`<workspace>/progress.md`，首行绑定 plan 路径）是跨压缩的恢复图——"Controllers without one have re-dispatched entire completed task sequences"；executor 可从 SDD 切换到 executing-plans 且共享同 workspace/ledger（skills/subagent-driven-development/SKILL.md "Setup"、skills/executing-plans/SKILL.md "Setup", obra/superpowers@5bf4e780）。
- **Rulings, not stalls**：只有四类事允许停下问人——不可逆/破坏操作、安全敏感动作、worktree 外副作用（merge/push/publish）、plan 烂到每条路都是猜；其余一律 "Ruling: <what> — <why> — <what it costs if wrong>" 记 ledger 继续走；结束时全部 Ruling 必须汇入最终消息的 "Rulings I made" 清单（"A ruling that dies with the workspace was a decision made in secret"）（skills/subagent-driven-development/SKILL.md "Rulings, not stalls" 与 "Finish", obra/superpowers@5bf4e780）。

### 6. 其余纪律 skill

- `test-driven-development`（330 行）：铁律原文 "NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST"（skills/test-driven-development/SKILL.md:34）；"Write code before the test? **Delete it. Start over.**" 且列明 "No exceptions: Don't keep it as 'reference'… Delete means delete"（:37-43）；RED 的 "Verify RED - Watch It Fail" 标注 **MANDATORY. Never skip.**；GREEN 同样 MANDATORY，并规定 "Other tests means the project's suite, not just your file"（全量套件才算绿，RELEASE-NOTES v6.4.1 说明动机：12 次 probe 中 11 次只跑了任务点名的文件）；附 12 行 "Common Rationalizations" 表格与 "Red Flags - STOP and Start Over" 清单（skills/test-driven-development/SKILL.md, obra/superpowers@5bf4e780）。
- `verification-before-completion`：铁律 "NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE"（skills/verification-before-completion/SKILL.md:17）；五步 Gate Function（IDENTIFY→RUN→READ→VERIFY→ONLY THEN），"Skip any step = lying, not verifying"（:35）；Common Failures 表逐条列 "claim ↔ 所需证据 ↔ 不充分证据"（如 "Tests pass" 需要 0 failures 的输出，"Previous run, 'should pass'" 不算）（skills/verification-before-completion/SKILL.md, obra/superpowers@5bf4e780）。
- `systematic-debugging`：铁律 "NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST"（skills/systematic-debugging/SKILL.md:17）；**四阶段**强制顺序：Phase 1 Root Cause Investigation（含多组件系统的插桩取证法）→ Phase 2 Pattern Analysis → Phase 3 Hypothesis and Testing（单假设、最小改动）→ Phase 4 Implementation（先写 failing test 再修；修 3 次仍败则 "STOP and question the architecture"，与 human partner 讨论而非第 4 次尝试）（:48、:120、:143、:168、:198, skills/systematic-debugging/SKILL.md）；旁挂 `root-cause-tracing.md`、`defense-in-depth.md`、`condition-based-waiting.md` 与 `find-polluter.sh` 支撑文件。
- `using-git-worktrees`：Step 0 先用 `git rev-parse --git-dir/--git-common-dir` 检测既有隔离（含 submodule 守卫），优先 harness 原生 worktree 工具、退回 `git worktree add`，目录默认 `.worktrees/` 且 "MUST verify directory is ignored"（`git check-ignore`），最后跑 baseline 测试确认干净起点（skills/using-git-worktrees/SKILL.md, obra/superpowers@5bf4e780）。
- `dispatching-parallel-agents`："Use when facing 2+ independent tasks that can be worked on without shared state or sequential dependencies"——按问题域分组、同一响应内并发派发、回收后查冲突跑全量套件；明列 Don't use when（相关失败/需全局状态/共享状态会互踩）（skills/dispatching-parallel-agents/SKILL.md, obra/superpowers@5bf4e780）。
- `writing-skills`（681 行，自举元 skill）——**框架真正的机制所在**：hook 只保证 bootstrap 被读，而每个 skill 是一个"按目标失败模式塑造行为、并在 eval 场景里对模型行为验证过的工件"；失败模式决定修辞形态，这是它与"文档合集"的区别，也是写自有 skill 套件时可迁移的核心思想：
  - **SDO（Skill Discovery Optimization）**（:140-158）：load-bearing 句原文 "**The trap:** Descriptions that summarize workflow create a shortcut agents will take. The skill body becomes documentation agents skip."——这就是 `description` 只准写何时用、禁写做什么的原因（:102、:180 的 `NEVER summarize the skill's process or workflow`），是发现机制的设计决策而非文风偏好（实证：description 写 "code review between tasks" → agent 只做一次 review；改为纯触发条件 → agent 读流程图做两阶段 review）。
  - **Skill 写作 = 应用于散文的 TDD**（:39-45 映射表 + :635-657 检查单）：RED = 在无 skill 条件下跑 baseline 场景并逐字记录违规与合理化借口（"Run baseline scenario BEFORE writing skill"、"Document exact rationalizations agent uses"）；GREEN = 只针对记录的违规写最小 skill 再复测；REFACTOR = 堵新 loophole 至 bulletproof。铁律与 TDD 同文 "NO SKILL WITHOUT A FAILING TEST FIRST"，且明确适用于对既有 skill 的**任何编辑**。
  - **"Match the Form to the Failure"**（:466-470）：四类 baseline 失败各配一种形态——压力下违规 → prohibition + rationalization table + red flags；输出形状错 → "state what the output IS — its parts, in order" 的正向 recipe；漏掉必备元素 → 模板里的 REQUIRED 字段槽位；行为应视条件而定 → 绑定可观察谓词的 conditional。且 scope 限定（:480-482）：这套 prohibition 工具**只适用于纪律类失败**，对 shaping 类失败会 backfire（同节给出实测："the prohibition arm produced clearly more of the unwanted content than the recipe arm… trended worse than even the no-guidance control"）。另有低成本 wording micro-test（每变体 5+ 次 fresh-context 采样、必须带 no-guidance control、"Variance is a metric"）。
  - **刻意的说服学基础**（:484）："See persuasion-principles.md for research foundation (Cialdini, 2021; Meincke et al., 2025) on authority, commitment, scarcity, social proof, and unity principles."——skill 的语气（"This is not negotiable. You cannot rationalize your way out of this."）是文档化的影响技术的应用。
  - **Rationalization 表格的出处**（:518-534）："Capture rationalizations from baseline testing… Every excuse agents make goes in the table"——`using-superpowers` 的 Thought/Reality 表、TDD 的 12 行 Common Rationalizations 表都是这个模式的实例（skills/writing-skills/SKILL.md 各处行号, obra/superpowers@5bf4e780）。
- `diagnosing-superpowers`（v6.4.1 新增）：会话出了问题后的事后取证——每条 finding 必须带 `path:line`（"No citation, no finding"），七个 analyst 维度（skill-timeline、plan-adherence、repeated-work、stumbles、quality-evidence、request-conflicts、cost-and-time）各派一个 subagent；硬性自我约束 "No superpowers diagnosis"（只报告证据，不诊断框架本身）与多项 approval gates（skills/diagnosing-superpowers/SKILL.md, obra/superpowers@5bf4e780）。

### 7. 强制 vs 建议：本 note 最关键的区分

- **机械层（harness/进程真实执行，模型无法绕过）**：
  1. SessionStart 钩子的上下文注入（bash，四种信封，无条件 `exit 0`）——**注入发生与否是机械的，注入后模型读不读不是**（hooks/session-start:39-53, obra/superpowers@5bf4e780）。
  2. 各 harness 的插件加载与 skill 注册（manifest、`resources_discover`、`ctx.skill.transform`、skill 目录扫描）——决定哪些 description 行进入模型的可选工具面（§2-§3 各文件）。
  3. `skills/*/scripts/` 与 `scripts/` 下的 bash 工具（sdd-workspace / task-brief / review-package / bump-version / sync-to-codex-plugin / package-codex-plugin）——真实进程、真实 exit code（如 task-brief 找不到任务 exit 3、review-package range 非法 exit 3）。
  4. `claude plugin validate` 的结构校验（但仅 warning 级，见 §1）。
- **散文层（SKILL.md 正文，模型可以忽略）**：Iron Laws、HARD-GATE、fix-loop 上限、rationalization 表格、停止条件、"You MUST" 措辞——全部是写进上下文的**劝说文本**。框架没有任何运行时检查能发现模型跳过 TDD、没跑测试就声称完成、或自行裁决了本应问人的事；唯一的"检测"是 `diagnosing-superpowers` 事后取证和外部 eval lab 的事后评测（§8-§9）。写作者深知此边界：hook 只做注入，纪律全靠正文工程（`<EXTREMELY_IMPORTANT>`、Red Flags 表格、"Violating the letter of the rules is violating the spirit" 等措辞即为此设计，writing-skills 的 persuasion-principles.md 更直接引 Cialdini 研究）。
- **同一规则的三档执行力度（最有力的单条证据）**：`using-superpowers` 的 `<SUBAGENT-STOP>`（"If you were dispatched as a subagent to execute a specific task, ignore this skill."）是**纯散文**（skills/using-superpowers/SKILL.md:6-8, obra/superpowers@5bf4e780）。OpenCode 的插件注释明说为什么不信任它："the `<SUBAGENT-STOP>` note inside the bootstrap relies on model compliance, which is not reliable. Detect child sessions structurally instead: a parentID on the session is the child signal…"，实现为 `isChild = session.parentID !== undefined`（lookup 失败时显式 fail-open：继续注入、不缓存）（.opencode/plugins/superpowers.js:147-155、:197-204, obra/superpowers@5bf4e780）。即：**同一个 skill，在 opencode 上被结构检查替代，在 Claude Code / Pi / Hermes 上仍只靠那段散文**。这就是 enforcement-vs-advice 轴最干净的图解。
- 一行事实性对比（非评测）：OpenSpec 的确定性 CLI 半在本地挡结构错误（`validate --strict` 把 warning 升级为失败），Superpowers 没有任何等价物——它的"验证"全部发生在模型头部（对照姊妹篇 OpenSpec note §6）。

### 8. 自举：项目自己的规范与自己是否遵守

- 规范：`writing-plans` 规定计划存 `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`；`brainstorming` 规定 spec 存 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`（skills/writing-plans/SKILL.md、skills/brainstorming/SKILL.md, obra/superpowers@5bf4e780）。

### 9. 评测与测试：两层，且都不在 PR 路径上

- **没有 CI**：`.github/` 只有 `FUNDING.yml`、`ISSUE_TEMPLATE/`、`PULL_REQUEST_TEMPLATE.md`，**不存在 `.github/workflows/`**（本地实测（obra/superpowers@5bf4e780）：`ls -d .github/workflows` → No such file or directory）。push/PR 不触发任何自动化。
- **两层测试**（上游自己的划分，`docs/testing.md:5-6` 直引）：
  - `tests/` — "does the plugin's non-LLM code work? Bash + node + python integration tests for brainstorm-server JS, OpenCode plugin loading, codex-plugin sync, and analysis utilities." 枚举见 `docs/testing.md:9-22`：brainstorm-server 的 node 套件（auth/lifecycle/ws-protocol 等 8 个 test 文件）、opencode 的插件加载/bootstrap 缓存/工具注册 bash 测试、codex-plugin-sync、Kimi manifest 接线、SDD 的 description-recall 与集成测试（带 token 分析）、worktree 的 RED-GREEN-REFACTOR、explicit-skill-requests、diagnosing-superpowers 结构检查（docs/testing.md:9-22, obra/superpowers@5bf4e780）。性质是**插件基础设施的 shell/node 冒烟测试**，不是 skill 行为评测。
  - `evals/` — "do agents behave correctly on real LLM sessions?" **该目录不在本仓库**：`git ls-files evals` = 0 且 `evals/` 被 `.gitignore:13` 显式忽略（注释原文："Eval harness lives in its own repository, cloned into `evals/` for local development… It is not part of the published plugin, so the whole directory is ignored here."；`git check-ignore -v evals/` 命中 `.gitignore:13`）——干净 clone 里完全没有 eval harness（.gitignore:13, obra/superpowers@5bf4e780；本地实测）；它指向上游 `prime-radiant-inc/superpowers-evals`（原称 Drill），harness CLI 名为 **Quorum**——"drives real coding-agent CLIs through a Gauntlet QA agent and grades them against each scenario's acceptance criteria plus deterministic post-checks"，场景在 `evals/scenarios/<name>/`，每条 3-30+ 分钟、跑真实 LLM 会话（docs/testing.md:25-35, obra/superpowers@5bf4e780）。文档称其为 "Python harness" 而上游 repo 主语言是 TypeScript——**文档与 repo 不一致，按 mismatch 记录**（docs/testing.md:6 vs prime-radiant-inc/superpowers-evals repo 元数据, 本地核实）。
- **上游自己的诚实声明**（docs/testing.md:37 直引）："Quorum scenarios are slow (3-30+ minutes each) and run real LLM sessions in permissive modes… Only the static gates (`bun run check`, `bun run quorum check`) are safe for public CI; the natural follow-up remains a tiered model (static gates on PR, live sweep nightly + on-demand)."——即维护者自己承认 PR 门禁 CI 是未建的后续项。
- **Stale pre-commit**：`.pre-commit-config.yaml` 三个本地 hook 全部 scoped `files: ^evals/.*\.py$`，调用 `uv --project evals run ruff …`——而 `evals/` 在本仓库不存在，这三个 hook 在干净 clone 中永远不匹配任何 staged 文件，是**事实上的 no-op**（.pre-commit-config.yaml, obra/superpowers@5bf4e780）。这恰是"强制比看起来更薄"的又一实例。

## Recommendation

对评估"把 Superpowers 作为方法论资产引入"的项目（如本仓库）：

1. **它的全部可移植资产是 `skills/` 目录 + 三个 bash helper（sdd-workspace/task-brief/review-package）**。纯文本、零依赖、可进 git；helper 脚本有真实 exit code，可在任何有 bash+git 的环境工作。引入成本就是把这些文件放进项目并装一次对应 harness 的插件/包。
2. **对本 harness（Oh My Pi / pi-agent）机制最贴合**：`.pi/extensions/superpowers.ts` 就是为 `@earendil-works/pi-coding-agent` 写的（`pi.on("resources_discover")` 注册 + `pi.on("context")` 注入），`pi install git:github.com/obra/superpowers` 即装；但要注意 `piToolMapping()` 明确说 **Pi 核心没有标准 subagent 工具**，SDD/并行派发两条链路依赖可选的第三方 `pi-subagents` 包，未装时 skill 自己会降级为顺序执行（.pi/extensions/superpowers.ts `piToolMapping()`、skills/using-superpowers/references/pi-tools.md, obra/superpowers@5bf4e780）。
3. **把"机械层 vs 散文层"作为 adoption 判断的轴**：如果团队需要的是硬门禁（没跑测试就不许合并），Superpowers 不提供——它没有 CI、没有 PR 检查、连 frontmatter 校验都只有 warning；它提供的是被大量 eval 调优过的**劝说文本**（rationalization 表格、red flags、铁律措辞）。适合作为 agent 行为资产，不适合作为合规工具。
4. **ledger + brief + review-package 的文件化协作协议值得单独借鉴**：它解决的是"controller 上下文是稀缺资源"问题——任务文本、diff、报告全部落盘走文件传递，controller 只留状态行；且 plan-scoped workspace 防同名 plan 串台。这套协议与具体模型/harness 无关，可抽出来用在任何多 agent 流程里。
5. 若只是想要 TDD/调试纪律而不想要整套流程，**直接抄单个 SKILL.md 即可**——没有运行时依赖，每个 skill 自包含；但要接受上游维护哲学（不接受"合规性"改写，AGENTS.md）。

## Risks

- **散文层的效力随模型漂移**：全部纪律依赖模型读到并服从 `<EXTREMELY_IMPORTANT>` 注入；上游自己把 skill 当"行为代码"并用 eval lab 回归，但 eval lab（superpowers-evals/Quorum）**不在本仓库且无 CI**——使用者无法自行复现其行为声明，只能信任维护者的评测记录（docs/testing.md、AGENTS.md, obra/superpowers@5bf4e780）。
- **10 个 harness 专属打包产物 × 4 种 bootstrap 实现**（bash hook / pi TS / opencode JS / hermes Python）的重复代码面：任何注入语义变更要改多处；Hermes README 段自己承认 "Hermes has no post-compaction hook, so a very long session that compacts over its first turn loses the bootstrap"（README.md "Hermes Agent", obra/superpowers@5bf4e780）——compact 后 bootstrap 丢失是各 harness 的已知薄弱点（pi 用 `session_compact` 重注入、Claude 用 matcher `startup|clear|compact` 缓解）。
- **Bootstrap 单点注入**：实测 payload 仅 ~3.6KB（一个 skill 全文），其余 14 个 skill 的发现完全依赖模型主动用 harness skill 工具；对不存在名字的探针不会枚举清单（本地实测）——description 写不好（writing-skills SDO 节警告的反模式）整个库就静默失效。
- **SDD 的成本模型**：每任务 fresh implementer + reviewer + 最多 5 轮 fix + 终评，token 开销大；skill 自己给出对冲（batch 同形小任务、model tiering、turn count beats token price），但长 plan 上仍可能显著贵于 inline 执行（writing-plans 的 handoff 节也明示二选一的权衡）。
- 本 note 的本地实测为单点运行（node v24.21.0、claude CLI  present、同 SHA 克隆）：覆盖 hook 三分支输出、端到端注入、skill 注册/发现探针、`claude plugin validate` 正/反例、`.github/` 与 `evals/` 缺失核验；未实测 Muse/Kimi/Hermes/Antigravity 实机的加载行为（只读源码与 manifest）。`pi-subagents` 与 Quorum 的上游事实取自 registry/repo 元数据与上游文档，未在本机运行。
- 上游迭代极快（v6.4.1 一次 release 就新增 diagnosing-superpowers、重建 executing-plans、新增 3 个 harness），且明确 "main 是发布分支、开发在 dev"（AGENTS.md）——引用行号以 `@5bf4e780` 为准。
