## Question

审计视图存在的理由是什么——它回答哪些具体问题、为谁服务、支撑什么动作？这是全图的根：用户已指出「意义不明」的核心是审计目的本身未定义，而非单纯的受众或排版问题。

## 本票要决议的细节

1. **受众与目的**：auditor 是谁（审批者事后复核？外部合规？operator 自查？）；审计视图支撑什么动作（合规追溯 / 批准复核 / 事故定界 / 完整性核验）。
2. **问题清单（question catalog）**：枚举审计者带着来的问题，逐条裁定进/不进。候选：
   - 「谁在何时提交了什么命令、结果如何」→ 命令回执 + actor；
   - 「状态如何一步步演变」→ 工作流事件流；
   - 「当前展示的事实如何验证未被篡改」→ digest 链；
   - 「发生了什么异常、恢复了没有」→ 事故列表；
   - 「批准绑定了哪些精确事实」→ packet provenance。
3. **问题 → 数据面映射**：现有六块逐一判定——回答哪个审计问题（保留）、不回答任何问题（候选移除或迁出，归宿归 V05）。
4. **术语**：Audit View 写入 CONTEXT.md；与 Workflow Doctor（spec 故事 64：只读不变量检查权威）的职责边界划清。
5. **spec 重述**：用户故事 24 的验收语义按决议结果重写，作为 spec 的第一章。

## Resolution（2026-08-18，grilling 两轮；第二轮进行中随 Destination 重绘终止）

1. **受众**：Operator 自查（唯一首要受众；非审批者复核、非外部合规、非发布核查）。
2. **支撑动作**：合规追溯（唯一）。
3. **问题清单**（仅两条，其余候选全部不进）：
   - 「谁何时提交了什么命令、结果如何」→ 数据面：命令回执 + actor；
   - 「各角色 Task 实际执行了什么」→ 数据面：结构化后的运行事件。
   - 不进：状态演变（工作流事件流）、完整性核验（digest 链）、事故定界、批准复核（packet provenance）。
4. **Workflow Doctor 边界**：严格分工、互不重叠——机器不变量检查归 Doctor，人的历史追溯归审计视图；审计视图不嵌入 Doctor 结果。
5. **术语**：采纳草案——「Audit View（审计视图）：面向 auditor 的只读独立视图，按审计问题清单组织；展示可验证的操作记录、事件与 digest 事实；不含排障控件与模型过程」。
6. **后续**：目的收窄至两条问题后，视图存续价值受质疑，用户拍板将本图 Destination 从「重构方案」重绘为「删除审计视图」。本票决议作为删除决策的依据存档；第二轮连锁问题（digest 处置 / 移除确认 / spec 故事 24 重写）随重绘作废。
