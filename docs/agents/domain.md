# Domain Docs

工程类 skill 探索本仓库时，应当怎么消费它的领域文档。

## 动手之前先读这些

- **`CONTEXT.md`**（仓库根）：本仓库域模型的**单一来源**。它定义七层条目、两类边、字段、覆盖率、门禁、陈旧、确认，每条带 `_Avoid_`（该避免的同义词）与「已接受的代价」注。
- **`docs/adr/`**：读与你接下来要动的区域相关的 ADR（0001 自建不寄生 / 0002 资产与代码同仓 / 0003 极薄 CLI 必需 / 0004 架构元素是外部输入）。

**注意文件名**：本仓库的域词表叫 `CONTEXT.md`，不叫 `GLOSSARY.md`——这是既有约定（规格 #147 与全部 ADR 都这么指），**不要**另建一份 `GLOSSARY.md`，两份词表必然漂移。

领域文档缺失时（例如某个概念还没定），**安静跳过**：不要报缺失、不要主动建议新建。`/domain-modeling`（经 `/grill-with-docs` 与 `/improve-codebase-architecture` 抵达）会在真的定下术语或决策时按需补。

## 目录结构

单上下文仓库（本仓库）：

```
/
├── CONTEXT.md          ← 域模型单一来源
├── AGENTS.md
├── docs/
│   ├── adr/            ← 决策记录
│   └── agents/         ← 本文件所在处：给 agent 读的约定
├── baize/              ← 设计数据（条目的落点，跟项目走）
├── skills/             ← 十个 skill（harness 侧工具，不跟项目走）
└── src/ test/ probes/
```

## 用词表里的词

产出里点名某个领域概念时（issue 标题、重构提案、假设、测试名），用 `CONTEXT.md` 定义的那个词，别漂到它 `_Avoid_` 里列的同义词上。

需要的概念词表里还没有，这是个信号：要么你在发明项目不用的语言（重新想），要么真有缺口（记下来给 `/domain-modeling`）。

## 与 ADR 冲突时

产出若与既有 ADR 矛盾，**显式说出来**，别默默覆盖：

> _与 ADR-0004（架构元素是外部输入）矛盾，但值得重开，因为……_
