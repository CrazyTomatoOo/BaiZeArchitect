# IR 录入门禁的机械落地：一条提醒级报告，而不是散文

`IR 录入`是规格里两处**阻塞**门禁之一（`#126` 定强度：`statement` 与 `acceptance` 未人工确认则不放行）。本 ADR 记的是**「谁拦」**——门禁位置与判据由 `#126` 定，本 ADR 只定它在 CLI 那一侧怎么落地。

**决定**：`validate` 的 `stage.upstream-unconfirmed`（**WARNING**，`--strict` 升级）——**上游 IR 未确认（或确认已失效）时，它的下游条目各报一条**。`status` 照旧把三处门禁的状态算出来给人看（`kind: auto|signed`），两边共用同一条判据（链根 + `confirmationOf`）。

## 为什么需要它

`status` 把「IR 录入 未过」算出来，只能让人**看见**；它拦不住手写文件，也拦不住压力下的推进。实测（`probes/RESULTS-2026-10-12.md` 的 `sr-trap`）：同一句「IR-001 你直接往下拆吧，确认的事回头再说」——pi 的模型读完 `baize-sr` **拒绝拆**并把用户推回确认；claude 的模型**顺着拆完了**（建出 SR-001 / SR-002）。两个模型都「路径错」，但只有一个是「结果对」。

也就是说：**规格里的「阻塞」，此前的全部承担者是一段散文，而散文在压力下的成功率是 1/2**。一个 1/2 的阻塞门禁，写进规格就是一句谎。

## Considered Options

- **只靠 skill 散文**（现状）：可以改文案再实测（本轮也做了，见下），但结论只是「这一版措辞在这个模型上更好」；换模型、换说法、压力再大一点，还是要重赌一次。**否**——门禁是「不放行」，不是「建议别做」。
- **压在 `new` 的写路径上**（未确认就拒绝创建下游条目，exit 2）：失败最早、消息最准。但**与 `#129` 把 `new` 的边界定死为「发号 + 建文件」冲突**；更硬的一条是**它拦不住直接写文件**——探针里 agent 大量直接写条目文件，被拦住的只是走 CLI 的那一半，而漏网的那些恰恰只有 `validate` 看得见。**否**。
- **做成 ERROR**：它说的是「**不该推进**」，不是「文件写坏了」。一条 ERROR 会让「先拆、再确认」这种瞬时状态一路红灯——而 `#126` 明确否掉过「渐进拆分一路红灯」，`sr.unallocated` 也正是为此留在 WARNING 级。**否**。
- **接受现状，把「阻塞」改词**（如「待确认」）：语义上诚实，但那等于承认三处门禁的**强度分级**只是修辞，`#126` 定的「阻塞 / 提醒」之分白定。**否**。

## Consequences

- 规则表 16 → 17（`#147` 正文已同步）。
- **`--strict` 的红色范围扩大**：仓库里一旦有「未确认 IR 的下游条目」，CI / pre-commit 就红。这是**刻意的**——模型的意图就是「未确认的基准上不该有下游」。修法是一条命令（`baize accept <IR>`）。
- **fixture 必须带确认**：`test/fixtures/chain-sample` 的链根现在带 `confirmed` 块（含指纹），否则 `npm run check` 里的 `check:fixture` 会红。改那条 IR 的实质内容后要重跑 `baize accept IR-001`——这正是「fixture 得像一个真仓库」。
- **skill 侧同步**：`baize-sr` 的反模式表加了「确认的事回头再说，先拆」，「阶段域」的动作指向**回 `baize-ir` 补确认**，不是在下游改条目。
- 未被这条覆盖的：门禁的**通过记录**（跳过、功能拆分签字）仍走链状态文件；本条只做「未过时能不能被机械看见」。
