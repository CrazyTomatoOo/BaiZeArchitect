# 退役是一笔记录，不是一个状态：条目带着 by / at / why 退出推进，出边不再算履约（#194）

**决定**：

1. 退役写在条目自己的 frontmatter 里：`retired: { by, at, why, supersededBy? }`（形状照 `confirmed` / `reviewed`）。命令面是 `baize retire <id> --why "…" [--superseded-by <id>] [--undo]`；`by` 取 `BAIZE_USER`（未设时 `unknown`）、`at` 取当次时钟，都由 CLI 写，人只给理由。
2. **出边不再算履约**：退役 SR 的 `covers` 不算覆盖、退役 AR 不算承接 SR、退役场景 / 用例 / 功能项的认领不算认领；退役条目的产出义务（`sr.unallocated` / `sr.unclaimed` / `coverage.unrealized-usecase` / 功能点的五项字段齐备）随之豁免。
3. **进边由 `stage.upstream-retired`（WARNING）点名**，只报**直接**上游：人要么自己也退役、要么改挂到在做的上游。自己退役了、或不再挂着退役上游，这条就消失。
4. `retired` **不进指纹**（不进 `substantiveFields`）：退役不是实质内容的改变。链根退役后 `status` 把它算作**已了结**，IR 录入门禁不再挂起；`--undo` 后覆盖率、陈旧、门禁全部回到退役前。
5. `retired` 不进 `layers.ts` 的必填字段表：老版本 CLI 遇到不认识的键一律忽略，照常解析——**不升 `schemaVersion`**，`--json` 只增不改。
6. 记录不完整（不是映射，或缺 `by` / `at` / `why`）报 `field.retire-incomplete`（**ERROR**）：退役写着半截比没写更坏——读者无法判断谁在什么时候为了什么退出。

## 为什么需要它

删掉是模型里唯一能「结束」一条需求的动作，而它有三个代价（#194 的问题陈述）：

- **从模型里消失**：引用它的条目全部报 `ref.*`（#193 实测：删掉 IR-001，下游两条 ERROR），而「为什么没了」无处可问——git 能翻出内容，翻不出决定。
- **半途上线永远红**：不删就永远躺在 `validate --strict` 的告警里（`sr.unallocated` / `sr.unclaimed` / 覆盖率缺口）；删了又要修引用。人一旦学会忽略诊断，诊断就失效了。
- **`status` 分不清哪条在做**：链总览把做完的与在做的一样显眼；skill 的触发条件是结构判断（上一段产物存在、这一段不存在），做完的链会被当成「该拆下一段了」。

## Considered Options

- **把退役的条目搬进子目录（`baize/ir/archive/`）**：否。ADR-0002 定了「目录是位置，`parent` 边是语义」；搬走就是删——#193 实测它从模型里消失、下游报错，而且会被 `id.stray` 点名。归档语义压给目录位置，正是 ADR-0002 拒过的做法。
- **加状态枚举（`active` / `done` / `archived`）**：否。CONTEXT.md 明确「没有状态枚举」：进度归 `status` 现算，落盘的状态会漂移。退役只记「人做的决定」（谁、何时、为什么），「还在不在做」由它算出来。
- **删掉，靠 git 与发号账本**：否。账本记住号不复用（#193），但记不住「这条为什么退出」——理由是一次人工动作，不是能从现状推出的东西。
- **退役当作履约（退役 SR 的 `covers` 仍算覆盖）**：否。那样退役会变成糊住覆盖率的万能钥匙：线索显示已覆盖，缺口没人再看见。退役一个 SR，它上游的线索**重新变成未覆盖**——这是刻意的代价，逼人决定改派还是删线索。
- **进边报整棵子树**：否。一次退役会刷满整棵树；只报直接上游，再往上的同一件事由那条上游的直接下游去问。
- **退役记录进指纹**：否。进指纹会让退役把全部下游标成陈旧（噪音），`--undo` 之后陈旧又凭空消失——两次都不是实质内容变了。
- **`why` 做成枚举（`done` / `dropped` / `superseded`）**：否。「做完了」与「不做了」的后续动作相同（都不再产出、都要处理下游）；枚举会把人的理由挤进几个格子，而 `supersededBy` 已经承担了唯一需要机器读的那一种。

## Consequences

- 退役是**人的一笔记录**：`retired` 由 CLI 写、解释权在人；模型不再假装知道「这条是不是真做完了」。
- 退役后条目仍占着扫描与 `status` 的位置——归档不是模型动作。要它彻底消失，删掉（git 留历史，编号由发号账本记住）。
- 下游挂着退役上游时 `--strict` 会红（`stage.upstream-retired` 是 WARNING）：这是提醒「该有人做个决定」，与 `stage.upstream-unconfirmed` 同级。
- 覆盖率与陈旧都会随退役变化：退役一个 SR，缺口重新出现；`--undo` 立刻恢复。这条代价写在 `coverage.ts` 与 `stale.ts` 的注释里。
- 撤销退役就是「删掉那条记录」：模型里没有不可变的审批链，也不做审批级撤销——「确认」那一层只管「我看过了」，不管退役与否。
