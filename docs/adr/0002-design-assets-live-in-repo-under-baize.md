# 设计资产与代码同仓，根目录 `baize/`

设计资产（IR / SR / AR 与后续三层条目，加链的阶段状态）**与代码同仓**，根目录 `baize/`。条目是 markdown 文件：**可寻址的字段进 YAML frontmatter**（`id` / `title` / `parent` / `covers` / `allocates` / `acceptance` / 确认记录），**长文本进正文**（`statement`）。按层级分目录，链的成员关系**只由 `parent` 边表达**，目录不表达。并发交给 git。

理由是两条硬约束：

- **同仓**：追溯的本质是「设计条目 ↔ 代码」。同仓让 `git log` / `git diff` / PR 天然把设计改动与代码改动绑在一起；分仓会把「这条 SR 对应哪个 commit 的代码」变成需要人工维护的外键。
- **frontmatter 与正文的分界**：`covers: [IR-001#a1]` 要求验收线索有**稳定 id**，而 markdown 列表没有稳定 id（重排即断引用）→ `acceptance` 必须在 frontmatter；`statement` 是长文本，塞进 frontmatter 会逼出转义地狱 → 留在正文。

## Considered Options

- **独立 store 仓库**（一个 store 服务多个 repo）：否。没有任何多仓需求；「预留口子」是假便宜——抽象层要真做出来才有价值，真需要时迁移一次比长期维护空抽象便宜。
- **全部进 frontmatter**：否。`statement` 是长文本，YAML 里要转义换行与列表。
- **全部进正文**（frontmatter 只放 `id`）：否。这正是 OpenSpec 的路线（靠 `#### Scenario:` 标题寻址），代价是**用错 `#` 的数量会静默失败**——没必要继承这个脆弱性。
- **纯结构化文件**（YAML / JSON）：否。改一句 `statement` 时 diff 应当只显示那一句，纯结构化在长文本上 diff 最差。
- **按需求链分目录**（`chains/<chain>/ir/…`）：否。**目录结构是「位置」，`parent` 边是「语义」——让两者表达同一件事必然漂移**：单亲模型下改父是合法操作，改父就得搬目录，而搬目录断 git 历史、断引用。
- **阶段状态与条目混放**：否。阶段状态是**链级**属性，混进层级目录会让「一条链」散成六个文件。
- **文件锁**：否。跨机器场景下锁文件不共享，是假的；还会制造「锁没释放」的运维问题。
- **乐观并发**（版本号 / 内容摘要）：否。内容摘要 git 本来就有，再加一层等于把 git 的活重做一遍。
- **按编号前缀分片目录**：否。浏览这些目录的是 CLI 不是人眼；分片会把「id → 路径」从一条规则变成两条，此后每处按 id 找文件都要多一层拼接，收益为零。

## Consequences

- 一条需求链的六段产物**散在六个目录**里，纵览一条链要靠 CLI 的 `status`——这正是 `status` 存在的理由，不是缺陷。
- `acceptance` 用 **map 而非 list** 存（`a1: …`），这是让 `covers` 的引用在重排后不断的前提。
- CLI 的并发职责边界只是「别写坏文件」（原子写：临时文件 + rename）；判断「谁改了什么」是 git 的事。
- 后三层（场景 / 用例 / 功能）的目录名取决于「场景/用例/功能三层的挂载点与层级语义」工单的答案，不在本 ADR 内。
- 根目录名跟随 CLI 名：CLI 若改名，目录跟着改，不另立一套。
