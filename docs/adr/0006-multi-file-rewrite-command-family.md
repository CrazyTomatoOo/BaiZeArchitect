# 多文件改写命令族的纪律：默认 dry-run、只读清单、拒绝先于改写、原子性到单文件

`baize rename`（#172）是本套件第一条**多文件改写命令**——一次命令改写散布在多份条目文件里的引用；`baize migrate`（#178，旧模型搬到认领边）是第二条，复用同一套机制与先例。本 ADR 记的不是某条命令的语义，而是这一**命令族**的四条纪律，以后加第三个同类命令时照此执行，不必重新争论（#190 用户故事 36）。

**决定**：四条纪律，两条命令共同遵守。

1. **默认 dry-run**：只打印将改的文件 + 行 + 旧值 → 新值，加 `--write` 才落盘。「显式的破坏性操作」的落地方式就是这个默认值——破坏性永远要人再点一次头。
2. **只改条目，绝不写清单文件**：清单（`baize/architecture.yaml`、场景目录）由外部权威维护，本套件对清单永远只读（ADR-0004）。命令的真实语义不是「我改清单」，而是「你告诉我 old→new，我把条目里的引用跟上」——改名多半发生在别人那边，本仓只负责让自己的条目跟上。
3. **拒绝条件先于改写**：拿不准就不动手。`rename` 要求新 slug 已存在于清单，否则 **exit 2 且不动任何文件**；`migrate` 对无法判定的 `parent`（指向非 SR 或不存在的 id）**跳过并点名**，不猜。一次影响多份文件，先证明目标存在比事后报一屏 ERROR 便宜。
4. **原子性只到单文件**：单份文件要么整份改好要么不改；命令整体**没有跨文件事务**——所以第 3 条才必须是硬前提（被拒时目录零变化），也所以 dry-run 输出里给一句「建议先提交」，把回退交给 git（ADR-0002：「谁改了什么」归 git 管）。

## 为什么需要它

多文件改写是这套 CLI 里**唯一一类「写着写着就把别人的仓库改花了」的操作**。`new` / `accept` 只碰一份文件，错了好认；这类命令一跑就是一批条目，拼错一个 slug、认错一层边，代价是满屏事后才看见的 ERROR 和一次不好说的回退。域文档里那句「显式的破坏性操作」（`CONTEXT.md` 的受控清单一段）正是为这类操作立的，但散文挡不住实现层面的漂移——四条纪律写下来，第三个命令才有可直接照抄的规矩。

## Considered Options

- **撤回承诺，不做命令**（收回「改清单 slug 时 CLI 自动改写引用」）：否。那句是刻意的设计意图，只是没实现；按分工（机械规则在 CLI、判断在 skill），「改名后统一改写引用」本就该在 CLI（#172 Q1）。
- **默认落盘，加 `--dry-run` 才预览**：否。默认落盘等于把破坏性做成隐式——「显式」的是 dry-run 之外的 `--write`，不是反过来（#172 Q2）。
- **`migrate` 并入 `validate --fix`**：否。校验只报不写是既有边界，`--fix` 会把它变成半个改写引擎（#178 Q2）。
- **版本号文件标记旧模型**（`baize/.schema-version`）：否。识别规则唯一且现成——方案层条目的 `parent` 指向 SR，那条边在新模型里就是非法的；加版本号文件等于新增一份要维护的状态，违背「能算的不写」（#178 Q3）。
- **强制 `git clean` 才允许 `--write`**：否。「谁改了什么」归 git 管；命令只在 dry-run 输出里**建议**先提交，不做强制检查——工作区脏是用户的常态，不该成为门槛（#178）。
- **写两条 ADR**（rename 一条、migrate 一条）：否。同一个纪律、两个命令，写两条只会让它们日后各漂各的（#178）。

## Consequences

- 两个命令共用一份契约：默认 dry-run（打印 文件 + 行 + 旧值 → 新值）、`--write` 落盘、被拒或不适用时 **exit 2 且不动任何文件**；`rename` 要求新 slug 已在清单里存在，`migrate` 幂等（已迁移仓库再跑 = 0 处改动、exit 0）。
- **清单文件在任何命令下字节不变**——ADR-0004 的「只读」从一句立场变成可断言的行为（#172 验收线索 4）。
- 原子性到单文件意味着**没有跨文件事务**：拒绝条件（第 3 条）是唯一的前置保护，不能被「部分成功」稀释；被拒即全停。
- 命令族先例已立：以后任何第三个多文件改写命令（删条目等推迟项）默认继承这四条，质疑纪律本身要先推翻本 ADR，而不是在实现时另起一套。
- 域文档里「显式的破坏性操作」的承诺从此为真；skill 侧的两条清单话术（`baize-scenario` / `baize-ar`）统一为「对照清单改条目里的引用，重复改名或引用很多时用 `baize rename`」。
