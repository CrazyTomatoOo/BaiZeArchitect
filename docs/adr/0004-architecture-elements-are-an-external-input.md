# 架构元素是外部输入，不是本套件的产物

本套件**不生产**架构元素，也不回答「组件该怎么分」。`AR.allocates` 指向一份受外部维护的**受控清单** `baize/architecture.yaml`（`components: { <slug>: { name, description? } }`，形状于 #142 统一为受控清单统一约定），**标量、恰好一个**；`validate` 校验引用的 slug 存在于清单，否则 **ERROR**。

理由是**它是输入约束，不是产物**：本套件的手艺是「把一条需求逐层拆到功能点」——**按需求分解**；而组件划分是**按职责分解**，是另一门手艺，且是 AR 拆分的前提。把架构设计拉进来，等于把一张正交的图塞进这条链。

代价写在明处：本套件**不回答「组件该怎么分」**，使用者得先有架构——**链条的起点是「已有架构」，不是白纸**。这对「全量设计」的期待是一处落差，已记入地图的 **Out of scope**。

## Considered Options

- **本套件生产**（新增「架构设计」一段，排在 AR 拆分之前）：否。会扩地图目的地，并把一个正交、体量不小的能力拉进这条链。
- **分配时顺带产生**（拆到哪算哪）：否。就没有任何权威说「系统由哪些组件构成」——`validate` 只剩两种坏选择：不校验悬空（拼写错误永远查不出），或把拼错的名字当新组件（清单被污染）。
- **分层**（系统 → 子系统 → 组件 → 模块，父边）：否。分类用字段、分解用父边——**组件不「派生自」组件**，这里根本没有分解可言；层级是分类，所以是字段（`layer`）。
- **一条 AR 分配多个元素**（共担）：否。分配要消灭的正是「责任不清」；真共担应表达为**两条 AR 各挂同一 SR**，各自可追溯、可各自标陈旧。
- **悬空引用只报 WARNING**：否。清单是唯一权威，「引用的元素不存在」就是真的错了；一旦容忍，「拼写错误」与「清单还没同步」就再也分不开。
- **元素做成条目级**（`baize/components/CP-001.md`）：否。孤儿规则会把所有组件报成孤儿（组件没有 `parent`），等于给每一项造一个假父或开一条豁免。

## Consequences

- 地图 **Out of scope** 增加一条：**架构设计（组件如何划分）**。
- `allocates` 是**标量**（恰好一个元素 id），与 `parent` 同形——不是数组。
- 清单与「场景目录」是**同一类东西**（受外部维护的枚举），两者的形态与校验应统一，归「场景目录词表的形态与校验」工单。 → 已落地：两份清单共用一套读法（`src/catalogs.ts`），`ref.unknown-element` / `ref.unknown-catalog` 两条规则对称。
