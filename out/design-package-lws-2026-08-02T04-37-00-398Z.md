# DS subdomainPolicy 校验复用 LWS generalValidate 语义 + ComputeRevision 纳入 NetworkConfig

> 审批状态: accepted
> DS webhook 缺 subdomainPolicy 校验且 ComputeRevision 未哈希 NetworkConfig,致 subdomain 静默漂移

## 上下文
仓库 lws 是 Kubernetes LeaderWorkerSet + DisaggregatedSet 控制器(Go)。DisaggregatedSet (DS) 通过 DisaggregatedRoleSpec 内嵌 leaderworkerset.LeaderWorkerSetTemplateSpec,因此每个 role 拥有 role.Spec.NetworkConfig(含 SubdomainPolicy *SubdomainPolicy,枚举 Shared/UniquePerReplica)。LDS webhook 已有 DisaggregatedSetWebhook.validate() 遍历 spec.roles[i] 调用 validateRoleRolloutStrategy 等,但未对 networkConfig.subdomainPolicy 做校验。LWS webhook 在 ValidateUpdate 中已有 "cannot set subdomainPolicy as null" 语义(line 111-112),generalValidate 通过默认值兜底。revision key 机制:DS 用 ComputeRevision(roles) 计算,其 roleTemplate 仅哈希 Name + LeaderWorkerTemplate(line 145-147),不包含 NetworkConfig,故 subdomain 变更不会产生新 revisionKey。LWSManager.Create 用 config.Spec 原样下发子 LWS(line 65),LWS revision_utils.getPatch 已包含 networkConfig(line 289-290)并经 ControllerRevision 持久化。需求:为 DS 增加 subdomainPolicy 校验(拒绝 null、限制枚举),并使 subdomain 变更纳入 revision key。

## 需求
- 变更请求: 为 disaggregatedset 控制器增加 subdomain 字段校验,复用 generalValidate 与 revision key 机制

## 评审发现 (critic 独立 challenge)
- [medium/high] DS webhook 无 Defaulter(仅 WithValidator,disaggregatedset_webhook.go:38-40),而 LWS webhook 同时注册 Defaulter(leaderworkerset_webhook.go Default() 将 nil SubdomainPolicy 默认为 SubdomainShared)。架构方案提议在 DS ValidateCreate/ValidateUpdate 中对 'NetworkConfig 非 nil 且 SubdomainPolicy 为 nil' 直接返回 'cannot set subdomainPolicy as null',这比 LWS 更严格:LWS 对同样输入(networkConfig.subdomainPolicy 缺省/nil)会默认为 Shared 并接受,DS 则拒绝。验收标准 '复用 LWS generalValidate 的 null 检查语义' 的前提不准确——LWS generalValidate(leaderworkerset_webhook.go generalValidate)根本没有 null 检查,它依赖 Defaulter 兜底;真正的 null 检查在 ValidateUpdate(line 111-112)且因 Defaulter 先运行而几乎不会触发。这造成 DS 与 LWS 对同一 NetworkConfig 输入的行为不一致,用户可能被意外拒绝。 → 二选一:(a) 为 DS webhook 增加 Defaulter(镜像 LWS Default():nil NetworkConfig→默认 Shared),使 DS 与 LWS 行为一致,ValidateUpdate 仅作防御性 null 检查;或 (b) 明确文档化此更严格行为为有意设计(并在需求/验收标准中修正'复用 generalValidate null 检查语义'的错误前提)。推荐 (a) 以真正对齐 LWS 语义。
- [medium/medium] ComputeRevision 扩展 NetworkConfig 字段的向后兼容/升级影响分析不准确。架构称'旧无 NetworkConfig 的 role 仍哈希空值,与既有 revisionKey 不同但属预期升级行为',但哈希是否变化完全取决于 roleTemplate 新增字段的 json tag:若用 `json:"networkConfig,omitempty"`,nil NetworkConfig 被省略→JSON 不变→哈希不变→无强制 rollout;若不用 omitempty,nil 被序列化为 `"networkConfig":null`→哈希变化→所有现存 DS 在控制器升级后首次 reconcile 即触发全量 rollout。架构未指定 json tag,存在歧义且运维影响巨大。即便用 omitempty,显式设置了 NetworkConfig 的 DS 对象升级后仍会 rollout(此前该字段未参与哈希)。 → 在架构组件中强制指定 `json:"networkConfig,omitempty"`,并明确记录:(1) 从未设置 NetworkConfig 的 DS 升级后 revisionKey 不变、不触发 rollout;(2) 显式设置了 NetworkConfig 的 DS 升级后会触发一次新 revision 的滚动——这是预期但需在 release notes 标注的运维影响。
- [low/medium] dataDesignContent 与验收标准混淆了两套独立的 revision 机制。ComputeRevision(pkg/utils/disaggregatedset/utils.go:144)产出的是 DS 级 revision(disaggregatedsetv1.RevisionLabelKey,用于 LWS 命名 GenerateName),并非 ControllerRevision。ControllerRevision 由 LWS 控制器的 NewRevision/hashRevision(pkg/utils/revision/revision_utils.go)产出,且 getPatch(line 289-290)早已纳入 networkConfig,因此 LWS 级 revisionKey 今日即可捕获 subdomain 变更。架构称'使 subdomain 变更产生新 ControllerRevision'表述误导:ComputeRevision 改动只让 DS 创建一个新命名的 LWS,新 LWS 再由 LWS 控制器生成其自己的 ControllerRevision。验收标准把 GetRevisionKey(LWS 级,leaderworkerset.RevisionKey)与 GetRevisionRolesList(DS 级,RevisionLabelKey)并列归于'ComputeRevision 哈希输入需包含 NetworkConfig'是混淆。 → 明确区分两层:(A) DS 级 ComputeRevision→RevisionLabelKey/LWS 命名——本次改动层;(B) LWS 级 getPatch/hashRevision→leaderworkerset.RevisionKey——已就绪,无需改动。验收标准中 GetRevisionKey 的期望应改述为'由既有 getPatch 保证,本次不改'。
- [low/medium] 架构组件 #3(lws_manager.go '无需改动')虽正确,但未点明关键不变式:reconcileRoleSimple(disaggregatedset_controller.go:314-358)对已存在 LWS 仅 Scale,从不原地更新其 spec;spec 变更只能经 revision 变化→新 LWS 名→existing==nil 创建分支(line 331-343)传播。ComputeRevision 修复之所以有效,正是依赖此不变式。若未来引入 LWS spec 原地更新,仅靠 revision key 不足以传播 NetworkConfig 变更。 → 在架构方案中显式记录该不变式作为设计约束:'DS spec 字段变更通过新 revision 创建新 LWS 传播,非原地更新',并标注若未来支持原地更新需同步评估。
- [low/high] 证据行号与归因有小幅偏差:证据#1(disaggregatedset_webhook.go lineStart 71)中 line 71 实为 `hasExternal := false`,role 循环实际在 72-74(可接受但略偏)。组件#1 文案'复用 LWS generalValidate 的 null/枚举语义'将 null 检查错误归因于 generalValidate,实际在 ValidateUpdate(line 111-112);contextSummary 已正确说明,但组件描述与验收标准的措辞仍可能误导实现者。 → 修正组件#1 措辞为'复用 LWS ValidateUpdate 的 null 检查语义(line 111-112)与 CRD 枚举',避免实现者误在 generalValidate 中寻找不存在的 null 检查。
- [low/medium] 枚举运行时校验与 CRD 枚举重复且 webhook 级难以测试。SubdomainPolicy 已有 +kubebuilder:validation:Enum={Shared,UniquePerReplica}(leaderworkerset_types.go:249),API server 在准入前即拒绝非法枚举,故 DS webhook 的 field.NotSupported 分支实际为不可达死代码(除非 CRD 校验被绕过)。架构承认是'双重校验',但验收标准要求'合法 Shared/UniquePerReplica 通过'的 webhook 测试易写,'非法枚举被拒'的 webhook 测试在 webhook 层难以构造(CRD 先拒)。 → 保留运行时枚举校验作为纵深防御但文档化为冗余;测试策略聚焦 null 拒绝 + 合法值通过,非法枚举测试交由 CRD/webhook 集成测试或明确标注为防御性分支。
> 证据全部核实为真(7 条 evidenceCandidates 的文件路径、行号区间、符号均与仓库 HEAD 一致)。核心设计方向正确:ComputeRevision 纳入 NetworkConfig 确为修复 subdomain 静默漂移的必要且充分的改动(依赖 reconcileRoleSimple 仅创建/不原地更新 LWS 的不变式),getPatch 已持久化 networkConfig 故 LWS 级 ControllerRevision 无需改动。但存在三处需在审批前澄清的问题:(1) 最重要——DS 无 Defaulter 而方案直接拒绝 null SubdomainPolicy,比 LWS(默认为 Shared)更严格,与'复用 LWS 语义'的验收前提不符,建议补 DS Defaulter 或显式文档化此差异;(2) ComputeRevision 新字段的 json tag(omitempty)决定升级是否触发全量 rollout,架构未指定,影响重大;(3) 两套 revision 机制(DS 级 ComputeRevision vs LWS 级 getPatch/hashRevision)在 dataDesignContent/验收标准中被混淆。另有两处低优先级文档/归因偏差。方案可批准,但建议先就 Defaulter 一致性与 json tag/升级影响达成决策。
