# baize-scenario：场景分析

## 这一段产出什么

场景条目：一条需求被使用的一个具体情境，用 `refines` 认领 SR（必填、可多值，骨架里已备好这个字段）；按场景目录分类，引用清单里冻结的分类 id（建条目时 `--catalog`）。字段以 `baize new` 的骨架与 `baize validate` 的报告为准。场景可挂父场景（「主流程＋异常流程」的分支），但那不是从 SR 派生的父边。场景不过人工确认，完成条件 = 字段齐备 + `baize validate` 无 ERROR。

## 可测性判断（方案层各段共用，与 baize-usecase / baize-function 同文）

这条写清楚了没有——有明确输入输出、有可观测结果。它是方案层各段统一的质量标准：上游「好」的标准与下游不一致时，拆分就无法交接。判断不过 = 没写完：回去改条目，不要用更多文字解释。

## 核心判断：情境是否完整

情境要写到**单独看这条场景就能复述**：什么条件下成立、什么事件启动、一步一步走到哪、偏差与异常怎么办、结束后世界变成什么样。缺了哪块（骨架里哪个字段没想清楚），这条场景就没写完——「很明显所以不用写」是偷懒，不是省略。数组字段允许空：「看过了确实没有」是结论，缺字段是「没想」，两者校验上分得开，别混。

## 特有判断：分类是否名副其实

catalog 选的分类要经得起「按目录出报告」的检验：这条场景放进该目录，按目录读报告的人会不会在这里找到它。拿不准就回场景目录清单读各项的名称与说明再选。一个场景只归一个分类——分类的价值在分组互斥；需要多维时另建清单，不让一个字段装多个值。

## 反模式最小集

- 「这场景很明显，前置不用写」→ 省略前置 / 备选，把情境写成一句描述。（挂在：field 域——缺字段 = 没想，一句描述过不了字段齐备；可测性判断——一句描述没有可观测结果。）

## 报错往哪个方向动

- field 域：补字段；空数组只用于「看过了确实没有」。
- ref 域：catalog 指向的分类不存在、或 `refines` 认领的 SR 不存在——对照清单 / 条目核对后改条目里的引用；觉得清单里该有新分类，找清单维护人加，不自己塞。重复改名或引用很多时用 `baize rename` 自动改写全部引用，不手工逐条改。
- id 域：编号由 CLI 发号，不手写。
