# baize-function：功能拆分

## 这一段产出什么

两个层级。功能项：短名 + 一句话说明 + 功能域——只有这些，**薄是设计不是遗漏**；给它加职责字段会造成两处描述同一件事，漂移时无法判断哪个对。功能点：从功能项展开的最小可测单元，五项齐备（职责 / 输入 / 输出 / 业务规则 / 验收基准）。功能项通过 realizes 关联到用例（建条目时 `--realizes`）。

## 什么算做完

- 交给 CLI 的：每个功能点五项非空、每条用例都有功能点 realizes 它、无未复核的直接下游陈旧——`baize validate` 与 `baize status` 给出这些事实。
- 靠人的：功能拆分门禁要签字（见 `baize-review`）——「这套拆分足以支撑实现」是人的判断，agent 不能代签。

## 可测性判断（三段分析共用，与 baize-scenario / baize-usecase 同文）

这条写清楚了没有——有明确输入输出、有可观测结果。它是三段分析统一的质量标准：上游「好」的标准与下游不一致时，拆分就无法交接。判断不过 = 没写完：回去改条目，不要用更多文字解释。

## 核心判断：能力是否小到可独立实现

拿一条功能点问：它能不能被一个人一次实现、按验收基准验掉？五项里任何一项填出来是套话——职责说不清在做什么、输入输出对不上、验收基准不可判定——都说明还没拆到点。功能项保持薄：它是能力的名片，内容由功能点承载。

## 特有判断：分层是否正确

功能点是不是真的从功能项展开的：点的内容要在项的能力范围之内，装不进去说明分错了层。项下展不出点，说明这项不是一项能力——回 SR 层看它到底属于哪条需求，别硬造点凑数。功能域是分类字段、不是层：别用它再造一棵假树（假树会逼出假父边）。

## 反模式最小集

- 「字段差不多填了就行」→ 五项填成互相重复的套话，看起来齐备但不可验证。（挂在：field 域——套话在字段校验眼里就是空；功能拆分门禁——签字对着两张客观清单，套话填出来的清单没人签得过。）

## 报错往哪个方向动

- field 域：补五项；套话不算数，重写。
- coverage 域：哪条用例还没有功能点 realizes——补功能项 / 点；补不出来，回头质疑这条用例是否成立。
- ref 域：realizes 指向的用例不存在、或父指向错——改功能项条目的引用与层级归属。
- stale 域：上游改过、标了陈旧——先复核上游再动下游，见 `baize-revise`。
