# baize-validate：随时校验

## 什么时候跑

写完或改完**任何**条目后；过任何门禁前。没有「这次改动小不用跑」——小改动最常断引用（改一个 id、挪一条边都是小改动）。

## 结果按域读，按域行动

报错按域分组；域是稳定的分类，动作随之稳定。规则明细只增不改，别背条目，按域行动：

| 域 | 动作 |
|---|---|
| `ref.*` | 去改条目：指向的 id 错了，或目标不存在——父边、covers 指向的线索、allocates 指向的元素、认领边（`refines` / `satisfies`）指向的 SR、关联边指向的场景 / 用例 |
| `coverage.*` | 去看上游的义务清单：漏了哪条没被覆盖（IR 的验收线索、待承载的用例），逐条对账，该补条目补条目、该改指向改指向 |
| `field.*` | 去补字段。「没写」（absent）与「写了但空」（empty）是两条不同的报告，动作不同：没写 = 没想过这件事，把内容补上；写了但空 = 想过了但没有结论——只在「看过了确实没有」时允许留空，否则把结论补上 |
| `stale.*` | 去复核：先看上游改了什么，再决定下游动不动——链级行为，见 `baize-revise` |
| `id.*` | 按编号规则改标识；编号由 CLI 发号，别手写、别复用已删编号 |
| `stage.*` | 阶段类的事实动作不同：**跳过记录缺字段**（谁定的 / 什么时候 / 为什么）→ 把三样补齐；**上游 IR 未确认就有下游条目** → 去找人把那条 IR 确认掉（或回它那一段），不是改下游条目 |
| `catalog.*` | 受控清单本身坏了（解析失败、slug 不合法、name 缺失）——清单由外部维护：去找清单维护人改，不许自己往清单里塞 |

另有一类不属于域：**要人签字的门禁**——动作是去找人，不是去改条目。

## 级别怎么读

级别一律用 token：`ERROR` = 结构坏了，必修，默认就算失败；`WARNING` = 不拦，但必须看一眼——来源分两类，「算得出的」（上游 IR 未确认、SR 没有 AR 承接、SR 未被任何方案层条目认领、IR 验收线索太多该拆了）与「判不了的」（陈旧＝复核义务——模型判不了「看没看」，只能判「改没改」）；`INFO` = 只看不挡，`--strict` 也不升级。加 `--strict` 把 `WARNING` 也算失败——CI 和过门禁前用它。退出码：0 干净；1 有问题；2 是命令本身用错了（这种也会给出说明，先读说明）。

## 哪些算得出、哪些要找人

门禁里，IR 录入与 SR→AR 由事实现算（确认本身、分配齐不齐）——改完条目重跑 `baize status` 即重算；功能拆分是人的判断，留在 `baize-review` 找人签。

## Rationalization 表（压力下会替自己找的借口）

| 借口 | 为什么是假的 |
|---|---|
| 「这次改动小，不用跑」 | 小改动最常断引用——改 id、挪边、改清单引用，全是小改动 |
| 「反正都是 WARNING」 | `WARNING` 是「不拦但必须看一眼」：分配是架构决策、认领是拆分进度、陈旧是复核义务。它不是没事，是 CLI 把判断还给了人 |

Red flags：刚改完条目却想跳过校验；把 WARNING 数量当进度看。
