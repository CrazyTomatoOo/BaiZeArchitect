# baize-revise：上游变更后的回改

## 这是链级行为

上游条目改了，它的直接下游被标陈旧（下游跟着全部出边走，认领边也算——SR 的实质字段一改，认领它的方案层条目都是直接下游）。复核属于各段之外的链级动作，不属于任何一段——别把它塞进某段的流程里，也别在某段 skill 里重写一遍。

## 顺序：先看上游，再动下游

1. **看上游改了什么**：读改后的版本，对着你拆它时的理解，说清楚差异。
2. **判断对下游意味着什么**：这个改动要不要下游跟着动、怎么动——上游加一条线索，你该补覆盖；上游改了陈述，你该核对展开是否还成立。
3. **动完下游，重新认领**：对上游做复核方向的 `baize accept`，把你复核过的上游版本记下来，陈旧标记才消。

跳过第 1 步直接改下游 = 按旧理解回改，越改越偏；跳过第 3 步 = 改了但没复核，陈旧还在。

## 陈旧不会被时间清掉

陈旧比对的是内容指纹（陈述 + 验收线索 + 出边），不是时间：文件修改时间会随检出重置，git 只知道提交、不知道你看没看过。所以「先提交、回头再复核」不会让陈旧消失——它不会自己消失；一个会自己消失的警告比没有更危险，而这个警告恰恰不会自己消失。只有人对过上游、重新认领，才算数。

## 分级处理

直接下游的陈旧阻塞功能拆分门禁，逐条复核；传递闭包内的只提醒——它们可能被间接覆盖，先等直接下游复核完，再看闭包里的条目还需不需要动。

## Rationalization 表（压力下会替自己找的借口）

| 借口 | 为什么是假的 |
|---|---|
| 「上游改的是错别字，不算实质改动」 | 指纹只取实质字段——被标陈旧就是实质内容变了。觉得标错了，回第 1 步把「改了什么」说清；说不清，就是你还没复核 |
| 「把下游同步成上游的样子就行」 | 同步跳过了判断：下游是你的展开，不是上游的镜像。上游加一条线索，正确动作是补覆盖，不是重写下游 |
| 「先提交，回头再复核」 | 陈旧比对不看时间：提交不会让标记消失，只会让待复核的债在链上越积越多 |

Red flags：没读上游改动就动下游；用提交压掉陈旧标记。
