# baize-usecase：用例分析

## 这一段产出什么

用例条目：一个目标导向的交互，用 `refines` 认领 SR（必填、可多值，骨架里已备好这个字段）。字段以 `baize new` 的骨架与 `baize validate` 的报告为准。用例与场景靠关联边相连：这条用例出现在哪些场景里，记在用例自己上（建条目时 `--appears-in`）。用例不过人工确认，完成条件 = 字段齐备 + `baize validate` 无 ERROR。

## 可测性判断（方案层各段共用，与 baize-scenario / baize-function 同文）

这条写清楚了没有——有明确输入输出、有可观测结果。它是方案层各段统一的质量标准：上游「好」的标准与下游不一致时，拆分就无法交接。判断不过 = 没写完：回去改条目，不要用更多文字解释。

## 核心判断：目标能否被系统达成

谁发起（actor）、要达到什么（goal）、成功之后世界变成什么样（后置承诺）。goal 是这条用例存在的理由，后置承诺是对结果的承诺——两者落成空话，这条用例就是场景的复读。用例必须与场景形状不同：字段也一样，那一级就没有存在的必要，只是把同一个东西写两遍。写每一条时问：删掉这条用例，会不会丢失一个场景说不清的交互目标？不会 = 它不该存在。

## 特有判断：服务了哪些场景

appearsIn 漏了没有：这条用例出现在哪些场景里，逐条挂上。挂少了 = 场景–用例的追溯网有洞，反向查「这个场景有哪些用例」时会漏。反过来，一条场景下提炼不出任何用例，该问这条场景是不是假场景（回 `baize-scenario`）。关联只记在用例上（后创建的一方）：补挂关联只改用例这一个文件，别去动场景。

## 反模式最小集

- 「跟场景差不多，抄一份改改」→ 写出与场景同形的用例，goal 与后置承诺是空话。（挂在：field 域——空话在字段校验眼里就是空；coverage 域——用例本身在上游义务清单里，每条用例要有人承载实现，复读出来的用例会把这份义务变成形式。）

## 报错往哪个方向动

- field 域：补字段；goal / 后置承诺写成空话 = 没写完，回去重写，不是补一个字数。
- ref 域：appearsIn 指向的场景、或 `refines` 认领的 SR 不存在——核对后改用例条目里的引用。
- coverage 域：「用例没人承载」属于功能拆分段的事，见 `baize-function`——本段只负责把用例本身写对、挂全。
