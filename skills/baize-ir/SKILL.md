# baize-ir：IR 录入

## 这一段产出什么

一条 IR 条目：一句话陈述 + 至少一条验收线索。`baize new ir` 发号建文件，内容你填。IR 是链顶端，没有父条目；一条链从一条 IR 起。

## 什么算做完

- 交给 CLI 的：各必填字段非空、编号合法——跑 `baize validate` 确认。
- 靠人的：陈述与验收线索要人确认（`baize accept`）。未经确认不算录入完成——IR 录入门禁挡的就是这一下。其余字段（短名 / 优先级 / 来源 / 理由）你起草即可。

## 核心判断：什么算一条需求

不是一个愿望（「希望系统更好用」拆不出可负责的单位），也不是一整块业务（「订单管理」是一坨，不是一条）。一条 = 一个可独立标识、独立引用、独立追溯的诉求：说得清谁在什么条件下要系统做什么。拿不准就拆——条目多了可以合，一大坨没法拆。

## 特有判断：什么算一条好的验收线索

可证伪、可观测：能指着一次运行结果说「过了 / 没过」。「能正常使用」「尽量快」不是线索，是愿望。线索逐条可寻址，是下游覆盖率的对账基准——基准写成空话，整条链的覆盖校验就是空的。线索太多（约七条以上）是「该拆了」的信号：拆成多条 IR，别合并成不可证伪的大话。

## 反模式最小集

- 「这块业务先记下来待拆」→ 一整块诉求当一条 IR，验收线索写成「能正常使用」。（挂在：field 域——空与空话都过不了字段校验；coverage 域——线索是下游逐条对账的基准；IR 录入门禁——人要对着陈述与线索签确认，别把人的确认浪费在空话上。）

## 报错往哪个方向动

- field 域：补字段。「没写」与「写了但空」是两条不同的报告：没写 = 没想过这件事；写了但空 = 想过了没有结论——验收线索不允许「看过了确实没有」，至少一条。
- coverage 域：在 IR 这一段出现，说明线索写法本身有问题（不可寻址、不可判定），回去改线索，不是改下游。
- ref 域：IR 无父，出现指向类错误说明条目层级建错了，去改条目的层级归属。
- id 域：编号由 CLI 发号，不手写、不复用已删编号。
